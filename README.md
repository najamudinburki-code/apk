# System Health 0.5.0

A buildable Android app, authenticated Node backend, and responsive web dashboard.

For fast local edits, use **LOCAL-DEVELOPMENT.md**. Windows shortcuts: **SETUP-DEV.cmd** once, **START-DEV.cmd** daily, and **CONNECT-PHONE.cmd** for USB. Choose the separate **System Health Dev** (`dev`) app to test against your laptop; normal debug/release variants keep Render. Give each AI **PROJECT.md** with its assigned file.

Version 0.4.0 adds Connect → Permissions → Check setup, verified connection and acknowledged-upload status, a simpler home screen with Advanced settings, and a front-camera default with the rear option retained. It is compatible with the existing API version 4 backend; this update does not require another Render deployment.

Version 0.5.0 still speaks API version 4, so the phone keeps working against your already-deployed backend; redeploy the backend and dashboard to get the new dashboard tabs, `request_settings`, exports and session revocation. The phone now has one upload path: every report, capture and health sample enters a file outbox that survives a crash, sheds only superseded samples when it is full, and keeps anything the server refuses on the phone instead of losing it. Tool requests answer with delivery truth (`running` only when the phone started it, `completed` only once the output reached the server, `reviewed` when the owner read the report and did not share it) and link to the stored record. Photo and microphone requests are captured in the background without opening the app; screenshots, file picking and a new boundary still need the visible screen and the owner's approval. The dashboard adds a paged activity log, one-click "Sign out everywhere", device rename and disable, CSV/JSON exports, a geofence form, per-phone "Phone rules" (a rule can only reduce what the phone does for you), and shows which APK release the server expects. The phone reports the rules it obeys, can repeat chosen reports on a schedule the owner starts, and tells its owner when a newer APK is available. Backend retention sweeps old events, files and finished requests, and dashboard sign-ins can be revoked server-side.

Installation page: **https://system-health-install.jkrick33.chatgpt.site** (private to your ChatGPT account). Start with **START-HERE.md**. The ready APK is supplied separately as **SystemHealth-debug.apk**.

- Open `android/` in Android Studio to build the app.
- Deploy `backend/` to the existing Render Node Web Service.
- Deploy `dashboard/` to the existing Render Static Site.
- PostgreSQL on Neon keeps enrollment, events, shared files and requests persistent. Local development also supports SQLite.

App text/notification sharing defaults to **All supported apps automatically**. No package-name entry is required; new supported apps are covered as they generate events. **Choose apps by name** remains available. The choice is saved and backed up, while active sharing requires approval and Android access permissions.

The APK contains the public Render server address and an enrollment-only invitation; the matching invitation hash is bundled in the backend. On first launch, each phone generates its own encrypted credentials and connects automatically without dashboard approval or typed configuration. Health monitoring starts after Android notification permission. Deploy the matching backend/dashboard once; no new required server environment variable is needed. Existing enrollments, legacy approval, advanced manual settings and Stop behavior remain.

The Android tools have visible controls and upload paths for camera, microphone, one-shot screenshots, location/geofences, nearby Wi-Fi/Bluetooth scans, and one file at a time from a folder you approve in Android's picker. The dashboard displays readable text, maps, files, requests, scans and received logs. Remote requests run as soon as the phone picks them up; Android still gates camera, microphone and screenshot access with its own permission dialogs.

Earlier Kotlin sources and function names remain except for what this round deliberately replaced: the socket upload stack (`SyncManager.kt`, `NetworkMonitor.kt`), which collapsed into the single HTTP path in `FeatureBridge.kt`; the duplicated scanner (`EnvironmentScanner.kt`), now one `HeadlessScan.kt`; the deleted request-notice policy, which the silent auto-run flow replaced; and the three tools the owner asked to have gone on 2026-10-07 — the local security audit (`SecurityAuditTool.kt`), the settings backup/export/restore pair (`SettingsBackupTool.kt`) and the single-document file picker. `docs/FILE-MAP.json` marks each of those rows. Original archives and alternative implementations remain under `archives/` and `variants/`. Older prototype dashboard component files were removed as unused; `FeaturePanels.jsx` implements the integrated authenticated tool panels and `ActivityLog.jsx` the paged history.

Checks that actually ran here: backend `npm test` 39/39 on SQLite; Android 49 unit checks with zero failures in both the `dev` and `debug` variants; `assembleDev`, `assembleDebug` and `assembleRelease` build; `lintDev` and `lintDebug` report zero errors with nonblocking warnings remaining; the dashboard production build succeeds. The rules flow was exercised in a browser against a throwaway local backend and temporary database. On 2026-10-07 a physical TECNO Camon 20 (Android 14) also ran the `dev` build against a local development backend: headless photo and microphone capture, installation as an update, scheduled reports and the dashboard rules round trip all behaved, and the session found and fixed three real bugs. That is not release readiness — reboot, accessibility and notification-listener extraction, Doze, this OEM's screen capture, geofence entry and the release-signed APK against Render still need the phone checks in `START-HERE.md`. This bundle supplies a debug/test APK; the release build is unsigned until you add your own key, and production publishing needs your signing plus device validation.
